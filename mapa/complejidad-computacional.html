⏱️ Complejidad computacional

Guía de referencia para predecir si un programa pasa en tiempo y memoria antes de escribirlo. La versión introductoria y con práctica guiada está en la ruta: 07 - Cuánto se demora tu programa. Volver a Temas.

El modelo: contar operaciones

Un juez ejecuta del orden de 10⁸ operaciones simples por segundo (con límite típico de 1–2 s). “Operación simple” = una suma, una comparación, un acceso a arreglo. El análisis consiste en estimar cuántas veces corre el trabajo interno de tu código en el peor caso — el juez siempre trae ese caso, diseñado con cariño para matarte.

Cómo contar: tres reglas

Casi todo el análisis sale de aplicar estas tres:

  1. Ciclos anidados multiplican. Un for de n dentro de otro de n es n·n.
  2. Bloques en secuencia: manda el peor. O(n) seguido de O(n²) es O(n²) — por eso optimizar la parte barata no cambia nada.
  3. Un ciclo que duplica (o divide) es logarítmico. Avanzar i *= 2 llega a n en ~log₂ n vueltas: para n = 10⁶ son 20, no un millón.

⚠️ El que engaña: for (int j = i; j < n; j++) dentro de un ciclo de i recorre “medio cuadrado” (n²/2 pasos), pero O grande ignora el /2 — sigue siendo O(n²). Ojo con creer que es lineal porque el interior “es más corto”.

Notación O grande

O(f(n)) describe cómo escala el trabajo cuando n crece: se queda solo el término dominante y se ignoran las constantes (O(3n² + 5n) = O(n²)). Eso hace el análisis portable entre máquinas… y también significa que las constantes no son gratis en la práctica (ver Trampas, abajo).

Si quieres el rigor: formalmente, f(n) es O(g(n)) si existen constantes c y n₀ tales que f(n) ≤ c·g(n) para todo n ≥ n₀. Como es una cota superior, decir que la búsqueda binaria es “O(n²)” es técnicamente cierto e inútil: siempre se busca la cota más ajustada.

De la restricción al enfoque (la tabla de decisión)

Léela al revés: el enunciado te dice n, tú deduces qué complejidad te están pidiendo:

RestricciónTe están pidiendoSospecha de…
n ≤ 11O(n!)permutaciones por fuerza bruta
n ≤ 20–25O(2ⁿ)subconjuntos, bitmask
n ≤ 500O(n³)DP cúbica, Floyd-Warshall
n ≤ 5 000O(n²)DP cuadrática, comparar todos los pares
n ≤ 2·10⁵O(n log n)sort, estructuras, búsqueda binaria
n ≤ 10⁷O(n)un recorrido, prefijos
n ≤ 10¹⁸O(log n) / O(√n) / O(1)matemática, búsqueda binaria sobre la respuesta

Por qué las dos tablas no dan los mismos números

El catálogo de arriba dice hasta dónde aguanta cada clase; esta dice a qué apuntar cuando lees el límite del enunciado. Por eso O(n log n) aparece como 10⁶–10⁷ allá y como 2·10⁵ acá: con n = 2·10⁵ apuntas a n log n con holgura de sobra, aunque la clase estire bastante más. Cuando el límite cae justo en el borde, gana la tabla de arriba.

Con consultas: n elementos y q consultas piden casi siempre O((n+q)·log n) — precalcular + responder cada consulta en O(log n). Y en problemas con subtareas, esta tabla se aplica por subtarea: cada límite más chico es una invitación a puntos con un enfoque más bruto.

El costo de tus herramientas (STL)

Un resumen para tenerlo a mano. La versión autoritativa —operación por operación, estructura por estructura, y generada desde los datos del vault— es el Catálogo de estructuras: si alguna vez estas dos no coinciden, manda esa.

OperaciónCosto
v.push_back(x)O(1) amortizado
sort(v.begin(), v.end())O(n log n)
set/map: insert, count, erase, []O(log n)
priority_queue: push, popO(log n)
lower_bound en vector ordenadoO(log n)
unordered_set/unordered_mapO(1) promedio, O(n) peor caso
concatenar strings con s = s + tO(largo(s)+largo(t)) — ¡en un ciclo se vuelve O(n²)! (usa s += t)

Amortizado significa “caro a veces, barato en promedio garantizado”: n push_back cuestan O(n) en total aunque alguno realoque y copie todo. El análisis amortizado también justifica patrones como two pointers: cada puntero avanza a lo más n veces en total, aunque una iteración avance mucho.

Sobre unordered_*: útiles y legales, pero su O(1) es promedio — en Codeforces existen tests anti-hash que las degradan a O(n). Con set/map (O(log n) garantizado) nunca te llevas esa sorpresa. El Syllabus IOI además deja las tablas hash fuera del conocimiento exigido.

La memoria también cuenta

Límite típico: 256 MB. Un int son 4 bytes; un long long, 8.

  • vector<int> de 10⁶ → ~4 MB ✓
  • vector<long long> de 10⁷ → ~80 MB ✓ (justo)
  • matriz de 10⁴ × 10⁴ de int → ~400 MB ✗ (repiensa el estado)

Si tu DP o tu matriz no cabe, no es un detalle: es el problema diciéndote que el estado está mal elegido.

Trampas reales de TLE (con la complejidad “correcta”)

  • endl vacía el buffer en cada línea: usa "\n". Y parte main con ios::sync_with_stdio(false); cin.tie(nullptr);.
  • Pasar contenedores por copia: void f(vector<int> v) copia todo en cada llamada — pásalo por referencia (const vector<int>& v, ver Punteros y referencias).
  • Constantes grandes: map es O(log n) con constante pesada; si las llaves son 0..n, un vector como arreglo de frecuencias es 10× más rápido.
  • Recursión profunda: sobre ~10⁵–10⁶ llamadas apiladas arriesgas stack overflow (RTE); un DFS sobre 10⁶ nodos en línea puede necesitar versión iterativa.

Ejemplo de análisis completo

“n ≤ 2·10⁵ precios y q ≤ 2·10⁵ consultas: ¿cuántos precios ≤ x?” Fuerza bruta: O(n·q) = 4·10¹⁰ ✗. Plan: sort O(n log n) + upper_bound por consulta O(log n) → total O((n+q) log n) ≈ 7·10⁶ ✓. Ese razonamiento — costo total, no costo por línea — es el hábito que esta guía quiere instalar.

🧪 Autoevaluación

Di la complejidad de cada uno antes de abrir la respuesta.

Respuesta 1

O(n·m), no O(n²): son dos variables distintas. Si m es chico (por ejemplo 3), el ciclo es en la práctica lineal en n.

Respuesta 2

O(n² log n): ordenar cuesta O(n log n) y lo estás haciendo n veces. Ordenar dentro de un ciclo es de los TLE más frecuentes — casi siempre basta ordenar una vez antes del ciclo.

Respuesta 3

O(√n): la condición i * i <= n es lo mismo que i <= √n. Para n = 10¹⁶ son 10⁸ vueltas… justo en el límite; para n = 10¹² son 10⁶, cómodo.

Respuesta 4

O(n²): hace n(n+1)/2 pasos ≈ n²/2, y la constante ½ se ignora. Es el caso que engaña de la regla 3.

Respuesta 5

O(n log n): cada insert es O(log n) y hay n. Mismo orden que un sort, pero con constante más pesada (por eso, si solo necesitas ordenar, sort gana).
