07 · ¿Cuánto se demora tu programa?

Buscar soluciones eficientes · Ruta de Aprendizaje

Antes de empezar. Ciclos y recorridos de arreglos: 03 - Arreglos y búsqueda lineal. No necesitas saber logaritmos: los interpretaremos como divisiones por dos.

🎯 Objetivos

Al terminar este módulo sabes:

  • Estimar cuántas operaciones hace tu código (notación O grande, sin sustos).
  • Estimar con las restricciones si un enfoque es viable antes de programarlo.
  • Reconocer cuándo un ciclo se reemplaza por una fórmula.

📖 La lección

Qué significa ese logaritmo

log₂(n) responde cuántas veces podemos dividir n por dos hasta llegar a 1: 8 → 4 → 2 → 1 necesita tres pasos, así que log₂(8) = 3. Duplicar n agrega solo un paso. Por eso O(log n) crece mucho más despacio que O(n). En O(n log n) se combinan ambos factores; la base del logaritmo solo cambia una constante y se omite en la notación.

Contar operaciones

La complejidad no es magia: es contar cuántas veces corre el trabajo interno.

Dibujado, cada vuelta del cuerpo es una casilla:

Desliza el diagrama para verlo completo.

Un ciclo con n iteraciones de trabajo constante es O(n). En el ejemplo, cada una de las n vueltas exteriores ejecuta n vueltas interiores: O(n²). Anidar ciclos no basta para concluir eso; hay que mirar sus límites y cuánto trabajo hace cada vuelta. Ordenar con sort es O(n log n) y buscar binariamente en un arreglo ordenado es O(log n). Una fórmula con un número fijo de operaciones sobre enteros de tamaño fijo es O(1). La notación O grande describe cómo crece el trabajo, omitiendo factores constantes.

Al duplicar n, el primero duplica su trabajo; el segundo lo cuadruplica; el tercero agrega un paso. Dos ciclos uno después del otro suman sus costos; en el ejemplo anidado, cada vuelta externa repite todo el interno.

La regla de los 10⁸

10⁸ operaciones simples por segundo sirve como estimación inicial, no como garantía: influyen el equipo, la memoria y el tipo de operación. Con eso, la tabla del módulo 02 deja de ser receta y se vuelve obvia: si n ≤ 5000, n² = 2.5·10⁷ merece evaluarse; si n = 10⁵, n² = 10¹⁰ explota y necesitas n log n o mejor. En segundos, para n = 10⁵:

ComplejidadOperacionesTiempo aproximado
O(n)10⁵0,001 s bajo este modelo
O(n log n)≈ 1,7·10⁶0,02 s bajo este modelo
O(n²)10¹⁰100 s ❌ (el límite suele ser 1–2 s)
O(2ⁿ)inimaginableni lo intentes

Y el doble ciclo con n = 5000 hace 2,5·10⁷ iteraciones: sería un cuarto de segundo bajo esa estimación si cada vuelta hiciera una sola operación simple. Es un candidato razonable; el costo real del cuerpo y el límite del juez determinan si alcanza. La complejidad no es buena ni mala por sí sola: depende de n. Hazte el hábito: restricción → complejidad tolerable → recién ahí, diseñar.

De ciclo a fórmula

El problema Divisibility Problem (1328A) pregunta cuántos +1 hay que sumarle a a para que sea divisible por b. La versión con ciclo (while (a % b != 0) a++, pasos++) funciona… hasta que a = 1 y b = 10⁹. La versión O(1):

Desliza el diagrama para verlo completo.

a % b es cuánto te pasaste del último múltiplo; b menos eso es lo que falta para el siguiente. El % b final cubre el caso borde en que a ya es divisible: sin él, la fórmula diría “faltan b” en vez de 0. Este salto — “¿puedo responder sin iterar?” — es exactamente lo que las subtareas grandes premian.

Cuando quieras la versión completa — costos de la STL, complejidad amortizada, memoria y las trampas reales de TLE — está en la guía de referencia: Complejidad computacional.

🏋️ Práctica

Práctica directa: El siguiente múltiplo

Lee a,b con 0≤a≤10⁹, 1≤b≤10⁹. Imprime cuántos +1 faltan para que a sea múltiplo de b. Entrada: 10 6. Salida: 2.

Idea para comprobar tu solución

El resto es 4; faltan 6−4=2. El caso 12 6 debe dar 0: usa el resto final de la fórmula.

Un ejemplo para pensar

Para cada posición i de un arreglo de tamaño n, un ciclo interior revisa únicamente las tres posiciones siguientes que existan. Hay dos ciclos anidados: ¿el trabajo es necesariamente cuadrático?

Contar repeticiones, no niveles de indentación

Cada una de las n posiciones provoca a lo sumo tres revisiones: no más de 3n en total. Es O(n). Si el ciclo interior revisara todas las posiciones posteriores, haría (n−1) + (n−2) + … + 1 = n(n−1)/2 revisiones, que sí es O(n²). Lo decisivo es cuántas veces se ejecuta el cuerpo, no cuántos ciclos se ven en el código.
