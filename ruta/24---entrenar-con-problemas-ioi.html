🎯 Objetivos

Al terminar este módulo sabes:

  • Elegir problemas IOI a tu medida usando las estadísticas del vault.

  • Complementar la revisión del código con casos reproducibles mediante stress testing.
  • Usar soluciones oficiales y simulacros para profundizar lo aprendido.

📖 La lección

Este vault es tu gimnasio

Desde aquí, la ruta deja de ser una escalera y se vuelve un mapa: los Temas del vault (con su qué abarca / qué no), las páginas de algoritmo con implementaciones, y 72 problemas IOI reales (2015–2026) con enunciado, paquete oficial y estadísticas. La brújula de contenidos es el Syllabus IOI — entrena lo que entra, ignora lo excluido.

Cómo elegir problema (sin morir en el intento)

Cada nota de problema trae su línea de dificultad (media, cuántos sacaron 100, cuántos 0). Elige primero por prerequisitos y una subtarea alcanzable. Una media alta puede reflejar puntos parciales accesibles; el porcentaje de 100 describe resolución completa y es una señal distinta. Estas puertas de entrada están en el vault:

El formato IOI de verdad

Aquí los problemas no leen cin: implementas funciones que el grader llama, y en los interactivos conversas con él bajo un límite de llamadas.

Cada carpeta de problema del vault trae los graders y ejemplos oficiales para correr local. La guía completa del flujo (compilar con grader, probar, depurar) es Formato IOI y debugging — léela antes de tu primer intento serio.

La estrategia de subtareas, ahora en serio

Un problema IOI no se “resuelve o no se resuelve”: se cosecha. Lee todas las subtareas antes de programar; asegura las baratas (fuerza bruta del módulo 13 incluida). Cada restricción adicional puede habilitar una idea más sencilla; luego considera qué habría que cambiar para resolver el caso general.

Encontrar tus propios bugs: stress testing

Un veredicto WA no siempre muestra la entrada que falló. Comparar una solución rápida con una enumeración independiente puede producir un caso pequeño que sí puedas seguir a mano. Ambas versiones deben respetar el mismo problema y formato.

Un ejemplo completo: suma máxima no vacía

Lee n y n enteros; imprime la mayor suma de un subarreglo contiguo no vacío. Para este ejercicio, 1≤n≤100000 y cada valor está entre −10⁹ y 10⁹. La solución rápida usa Kadane del módulo 14. La fuerza bruta solo se ejecutará con n pequeño.

Una versión con error intencional inicia actual=0, actualiza actual=max(0,actual+x) y conserva la mayor suma. Para 3 seguido de -5 -2 -7, imprime 0: eligió el subarreglo vacío, prohibido.

La fuerza bruta enumera cada inicio l y cada final r≥l. No incluye intervalos vacíos:

Sus sumas candidatas son −5, −7, −14, −2, −9 y −7; la respuesta es −2. Se inicia el máximo con un elemento real, no con cero. Es O(n²), suficiente para comparar casos pequeños.

Descarga estos archivos en una carpeta de práctica:

  • sol_incorrecta.cpp: versión con el error que vamos a encontrar.
  • sol.cpp: versión corregida, que inicia con el primer elemento y decide entre empezar de nuevo o continuar.
  • bruta.cpp: enumeración anterior.
  • gen.cpp: con semilla 1 entrega el caso negativo anterior; con las demás, n entre 1 y 8 y valores entre −10 y 10.
  • stress.py: ejecuta ambos programas y conserva el primer fallo. Necesita Python 3.

La semilla es el argumento de ./gen 42: permite reproducir el mismo caso con el mismo generador. Se combinan un caso borde deliberado y casos aleatorios; el azar no garantiza encontrar un error.

El mismo algoritmo con una función y un grader

Como ejemplo didáctico, descarga suma_maxima.h, funcion.cpp y grader.cpp. El header declara suma_maxima(a); tu función devuelve el resultado; el grader aporta main, lee y escribe:

Imprime −2 para el caso negativo y permite reutilizar el mismo stress: el grader adapta la interfaz de función a entrada/salida. Este grader no valida la respuesta: solo la imprime; la comparación la hace el script con la bruta. En un problema IOI real usa la firma, restricciones, archivos y comandos de su paquete oficial; un interactivo puede requerir un manager distinto.

Desliza el diagrama para verlo completo.

Si aparece una diferencia, compara ambas salidas y revisa también la fuerza bruta. Tener dos programas no garantiza que uno esté bien. Conviene que la enumeración siga directamente la definición del problema y use una idea diferente de la optimización.

Los casos pequeños hacen viable la enumeración y facilitan reducir un contraejemplo. Después de corregir, conserva ese caso y vuelve a compararlo junto con otros límites y casos aleatorios.

Sirve para dos cosas distintas, y la segunda es la que casi nadie usa: depurar un WA, y buscar contraejemplos a un greedy todavía no demostrado — exactamente lo que te pidió el módulo 23. Si sobrevive mil casos, solo sabes que coincide en esos casos. Combina entradas aleatorias con casos límite y enumeración exhaustiva pequeña; después demuestra el greedy. Un contraejemplo sí basta para refutarlo.

Cuándo no aplica: en tareas interactivas (ahí el caso lo construye el manager, ver Formato IOI y debugging) y cuando hay varias respuestas válidas — en ese caso no compares las salidas con diff, sino escribe un tercer programa que verifique que tu salida cumple lo que pide el enunciado, y compárale solo el puntaje.

Aprovechar una solución oficial

Intentar ejemplos pequeños y una solución para alguna subtarea ayuda a leer la editorial con una pregunta concreta. Si una pista desbloquea el problema, puedes continuar desde ahí; no hace falta esperar un tiempo fijo.

Al estudiar una solución oficial, busca qué observación hace posible el algoritmo y por qué cubre todos los casos. Reimplementarla sin copiar permite poner a prueba esa explicación. Los simulacros de Simulacros son una opción para practicar también la selección de problemas y el uso del tiempo.

🏋️ Práctica

Práctica directa: Reproducir un contraejemplo

Ejecuta sol y bruta del ejemplo con entrada 3 / -5 -2 -7. La versión con el error imprime 0; la bruta imprime -2.

En los ejemplos de entrada y salida, / separa líneas; no se escribe en el archivo.

Idea para comprobar tu solución

Reduce a un solo elemento −2: el fallo persiste. El caso revela que la versión incorrecta permitía elegir el subarreglo vacío.

Aplicar en problemas

Los problemas siguientes requieren traducir un enunciado y pueden combinar otras ideas. Su procedencia e idioma no indican un orden obligatorio de dificultad.

Secuencias IOI propone un orden de problemas con pistas para avanzar cuando haga falta. Simulacros ofrece conjuntos para practicar en condiciones de competencia.

Un comienzo posible: Mutating DNA (entrada suave), Connecting Supertrees (construcción + DSU) y Combo (primer interactivo, con Formato IOI y debugging al lado). Después, el mapa es tuyo: navega por Temas según lo que quieras fortalecer.

Para pensar: una subtarea puede esconder un error

Quieres la suma máxima de un subarreglo no vacío. Tu solución parte con respuesta 0 y pasa una subtarea donde todos los elementos son positivos. Un stress test encuentra a = {−5, −2, −7}: tu programa devuelve 0 y la fuerza bruta devuelve −2. ¿Es un problema de velocidad o de definición?

Ver razonamiento

Es de definición: ningún subarreglo no vacío de esa entrada suma 0. La inicialización permite implícitamente elegir el subarreglo vacío, un caso prohibido. Con positivos el error queda oculto porque alguna suma supera 0. El caso se puede reducir a {−2} y sigue fallando: eso aísla la causa. Inicializar la mejor respuesta con el primer elemento y respetar el estado no vacío corrige esa idea. Pasar una subtarea demuestra comportamiento en sus restricciones; antes de extender la solución hay que revisar qué supuestos dejan de estar garantizados.
